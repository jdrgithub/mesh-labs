Here’s a clean “golden-path” you can copy and adapt: a Backstage Software Template that scaffolds a new app repo in GitLab, requests infra from Crossplane, and deploys to OpenShift using a GitLab CI pipeline.

Phase 1 — What this template does
Prompts the user for inputs (service name, owner, env, DB size, etc.).

Creates a new GitLab repo from a skeleton (Dockerfile, Helm chart/K8s manifests, .gitlab-ci.yml, app code).

Creates (or updates) an infra repo PR that adds a Crossplane claim (e.g., CompositePostgresInstance).

Registers the new service in Backstage’s catalog.

GitLab CI builds the image, pushes to GitLab Container Registry, then deploys to OpenShift using a service account.

Phase 2 — Prereqs / integrations
Backstage:

backstage-plugin-scaffolder with GitLab integration (integrations.gitlab[]) and actions (publish:gitlab, catalog:register).

Crossplane:

Running in-cluster on OpenShift.

Provider(s) configured (e.g., provider-aws for RDS, or on-prem providers).

An XRD + Composition for your DB (shown below).

OpenShift:

A namespace per app or per team.

A ServiceAccount with edit (or minimal RBAC) for deploys from CI.

GitLab:

Project/group access tokens or user PAT for Backstage to create repos.

CI/CD variables for OpenShift API, SA token, and namespace.

Phase 3 — Backstage Software Template (minimum working shape)
# templates/app-with-db/template.yaml
apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name: app-with-db
  title: "App + DB on OpenShift"
  description: "Scaffold a service, provision DB via Crossplane, deploy via GitLab CI."
spec:
  owner: platform-team
  type: service

  parameters:
    - title: Service details
      required: [name, owner, namespace, environment]
      properties:
        name: { type: string, title: Service name, pattern: '^[a-z0-9-]+$' }
        owner: { type: string, title: Backstage owner, description: "e.g. team:payments" }
        namespace: { type: string, title: OpenShift namespace }
        environment: { type: string, enum: [dev, staging, prod] }
        dbSize: { type: string, enum: [small, medium, large], default: small }

  steps:
    - id: fetch-base
      name: Fetch skeleton
      action: fetch:template
      input:
        url: ./skeleton
        values:
          name: ${{ parameters.name }}
          owner: ${{ parameters.owner }}
          namespace: ${{ parameters.namespace }}
          environment: ${{ parameters.environment }}

    - id: publish
      name: Create GitLab repo
      action: publish:gitlab
      input:
        repoUrl: gitlab.com?owner=platform-apps&repo=${{ parameters.name }}
        defaultBranch: main
        description: "Service ${{ parameters.name }}"

    - id: push-infra-claim
      name: Raise PR to infra repo with Crossplane claim
      action: publish:gitlab:merge-request
      input:
        repoUrl: gitlab.com?owner=platform-infra&repo=crossplane-claims
        title: "Add DB claim for ${{ parameters.name }}"
        branchName: feat/${{ parameters.name }}-db
        targetBranch: main
        commitMessage: "Add DB claim for ${{ parameters.name }}"
        # Render a claim file from a small template in ./infra-claim
        # placing it under claims/<environment>/<service>.yaml
        files:
          - source: ./infra-claim/claim.yaml
            target: claims/${{ parameters.environment }}/${{ parameters.name }}.yaml
        replacements:
          serviceName: ${{ parameters.name }}
          namespace: ${{ parameters.namespace }}
          size: ${{ parameters.dbSize }}

    - id: register
      name: Register in Backstage catalog
      action: catalog:register
      input:
        repoContentsUrl: ${{ steps.publish.output.repoContentsUrl }}
        catalogInfoPath: /catalog-info.yaml

  output:
    links:
      - title: "App repository"
        url: ${{ steps.publish.output.remoteUrl }}
Notes

fetch:template copies a skeleton folder (see Phase 5).

publish:gitlab:merge-request is a handy pattern to write infra to a separate repo (GitOps-style approval for infra).

Phase 4 — Crossplane (XRD + Composition + Claim)
XRD (once, in infra repo):

apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: compositepostgresinstances.platform.example.org
spec:
  group: platform.example.org
  names:
    kind: CompositePostgresInstance
    plural: compositepostgresinstances
  claimNames:
    kind: PostgresInstance
    plural: postgresinstances
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                parameters:
                  type: object
                  properties:
                    size: { type: string }
                    namespace: { type: string }
Composition (once, in infra repo):

apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: postgres.aws.default
  labels:
    crossplane.io/xrd: compositepostgresinstances.platform.example.org
spec:
  compositeTypeRef:
    apiVersion: platform.example.org/v1alpha1
    kind: CompositePostgresInstance
  patchSets:
    - name: size
      patches:
        - type: FromCompositeFieldPath
          fromFieldPath: "spec.parameters.size"
          toFieldPath: "spec.forProvider.instanceClass" # adjust to your provider
  resources:
    - name: rds-instance
      base:
        apiVersion: rds.aws.crossplane.io/v1beta1
        kind: DBInstance
        spec:
          forProvider:
            engine: postgres
            engineVersion: "15"
            publiclyAccessible: false
          writeConnectionSecretToRef:
            namespace: crossplane-system
            name: rds-${COMPOSITE_NAME}
      patches:
        - type: PatchSet
          patchSetName: size
Claim (generated by the template into the infra repo):

apiVersion: platform.example.org/v1alpha1
kind: PostgresInstance
metadata:
  name: {{ serviceName }}-db
  namespace: {{ namespace }}
spec:
  compositionSelector:
    matchLabels:
      provider: aws
      tier: default
  parameters:
    size: {{ size }}     # small|medium|large
    namespace: {{ namespace }}
After this merges, Crossplane reconciles and (example) provisions RDS, emitting a connection Secret (you can mirror it into the app namespace via External Secrets or a Crossplane Secret Store pattern).

kind: Route
metadata:
  name: ${name}
  namespace: ${namespace}
spec:
  to: { kind: Service, name: ${name} }
  port: { targetPort: http }
  tls: { termination: edge }
.gitlab-ci.yml (minimal)

stages: [build, deploy]

variables:
  IMAGE_TAG: $CI_COMMIT_SHA

build:
  stage: build
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$IMAGE_TAG .
    - docker push $CI_REGISTRY_IMAGE:$IMAGE_TAG

deploy:
  stage: deploy
  image: registry.access.redhat.com/openshift4/ose-cli:latest
  script:
    - oc login $OCP_API --token=$OCP_TOKEN --insecure-skip-tls-verify
    - oc project ${OCP_NAMESPACE}
    - sed -e "s#IMAGE_PLACEHOLDER#$CI_REGISTRY_IMAGE:$IMAGE_TAG#g" k8s/deployment.yaml | oc apply -f -
    - oc apply -f k8s/service.yaml
    - oc apply -f k8s/route.yaml
  environment:
    name: ${environment}
  only:
    - main
