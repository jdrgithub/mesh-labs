Rate Limiting
What It Is
Controlling how many requests a service accepts within a time window—either globally, per client, or per specific criteria (IP, user ID, API key, etc.).
Why You Need It

Protection from noisy neighbors: One customer's batch job hammers your API and degrades service for everyone
Cost control: External API calls cost money—limit them before your AWS bill explodes
Prevent cascading failures: Downstream service can handle 1000 RPS max; enforce that limit before it falls over
Abuse prevention: Stop scrapers, attackers, or misbehaving clients

Without Istio
You implement this in every service:
python# In each service's codebase
from flask_limiter import Limiter
limiter = Limiter(app, key_func=get_remote_address)

@app.route("/api/users")
@limiter.limit("100 per minute")
def get_users():
    # your logic here
Problems:

Each service needs the library and configuration
Different languages = different implementations
Redis/memcached needed for distributed rate limiting
Configuration scattered across codebases
No central visibility into rate limit enforcement

With Istio
Configure once at the mesh level:
yamlapiVersion: networking.istio.io/v1alpha3
kind: EnvoyFilter
metadata:
  name: rate-limit-user-service
spec:
  configPatches:
  - applyTo: HTTP_FILTER
    match:
      context: SIDECAR_INBOUND
      listener:
        filterChain:
          filter:
            name: "envoy.filters.network.http_connection_manager"
    patch:
      operation: INSERT_BEFORE
      value:
        name: envoy.filters.http.local_ratelimit
        typed_config:
          "@type": type.googleapis.com/envoy.extensions.filters.http.local_ratelimit.v3.LocalRateLimit
          stat_prefix: http_local_rate_limiter
          token_bucket:
            max_tokens: 100
            tokens_per_fill: 100
            fill_interval: 60s
Or use a simpler EnvoyFilter with global rate limiting service. The key: application code is unchanged. Rate limiting happens at the Envoy proxy before requests even hit your app.

Custom Retries and Retry Logic
What It Is
Automatically re-attempting failed requests based on specific conditions—HTTP status codes, timeouts, connection failures, etc.
Why You Need It

Transient failures are common: Network blips, pod restarts, brief unavailability
Improves reliability: 95% success rate → 99.7% with 2 retries (if failures are independent)
User experience: One failed request shouldn't fail the entire operation
Different failures need different strategies: Retry on 503, don't retry on 400

Without Istio
Implement retry logic in every HTTP client:
javascript// In each service
async function callUserService(userId) {
  let attempts = 0;
  const maxAttempts = 3;
  const backoff = [100, 500, 2000]; // exponential backoff
  
  while (attempts < maxAttempts) {
    try {
      const response = await fetch(`http://user-service/users/${userId}`);
      if (response.status === 503 || response.status === 429) {
        // Retry on these
        attempts++;
        await sleep(backoff[attempts - 1]);
        continue;
      }
      if (response.status === 500) {
        // Maybe retry, maybe not?
        attempts++;
        continue;
      }
      return response;
    } catch (error) {
      // Network error - retry
      attempts++;
      if (attempts >= maxAttempts) throw error;
      await sleep(backoff[attempts - 1]);
    }
  }
  throw new Error('Max retries exceeded');
}
Problems:

Copy-paste this across every service and every language
Inconsistent retry behavior (some services retry 3x, others 5x)
No visibility into retry rates
Retry storms: 10 services each retry 3x = 30x load on downstream
Hard to change retry policy (need to redeploy all services)

With Istio
yamlapiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: user-service
spec:
  hosts:
  - user-service
  http:
  - route:
    - destination:
        host: user-service
    retries:
      attempts: 3
      perTryTimeout: 2s
      retryOn: 5xx,reset,connect-failure,refused-stream
      retryRemoteLocalities: false
Benefits:

Configured once, applies to all callers
Change retry policy without touching application code
Envoy handles exponential backoff automatically
Per-try timeout prevents hanging retries
Observable: Envoy exports retry metrics (attempts, success rate)
retryOn conditions are sophisticated (connection refused, stream reset, specific status codes)

Circuit Breakers
What It Is
Automatically stop sending requests to a failing service for a period, then gradually test if it's recovered. Prevents cascading failures.
Why You Need It

Stop the bleeding: If a service is down, don't hammer it with requests
Fail fast: Better to return 503 immediately than wait for timeout
Protect upstream: Your retries shouldn't DDoS the failing service
Self-healing: Automatically resume traffic when service recovers

The Pattern:

Closed: Normal operation, requests flow through
Open: Too many failures detected, stop sending requests (fail immediately)
Half-Open: After timeout, send test requests; if they succeed, close the circuit

Without Istio
Implement circuit breaker logic in every service:
python# Using a library like pybreaker
from pybreaker import CircuitBreaker

payment_breaker = CircuitBreaker(
    fail_max=5,  # Open after 5 failures
    timeout_duration=60,  # Stay open for 60s
    exclude=[HTTPError400]  # Don't trip on 4xx
)

@payment_breaker
def charge_customer(amount):
    response = requests.post('http://payment-service/charge', json={'amount': amount})
    if response.status_code >= 500:
        raise Exception("Payment failed")
    return response.json()

# Now call it
try:
    charge_customer(100)
except CircuitBreakerError:
    # Circuit is open, handle gracefully
    log_error("Payment service unavailable")
    return {"error": "Payment temporarily unavailable"}
Problems:

Every service needs circuit breaker library
State tracking (circuit open/closed) needs to be distributed
Each service independently decides when to trip the breaker
No coordinated backoff across callers
Inconsistent thresholds across services

With Istio
yamlapiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: payment-service-circuit-breaker
spec:
  host: payment-service
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 10
        maxRequestsPerConnection: 2
    outlierDetection:
      consecutiveErrors: 5
      interval: 30s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
      minHealthPercent: 50
How It Works:

Outlier Detection: Envoy tracks error rates per pod
consecutiveErrors: 5: If a pod returns 5xx five times in a row, eject it
baseEjectionTime: 30s: Keep it ejected for 30s
maxEjectionPercent: 50: Never eject more than 50% of pods (prevent total outage)
Connection pooling: Limit concurrent connections to prevent overwhelming the service

Benefits:

Implemented at the proxy level—no application code
Works per-pod: Ejects unhealthy instances, keeps sending traffic to healthy ones
Coordinated across all callers (Envoy shares health state)
Metrics available: ejection counts, ejection duration
Tunable without code changes


Load Balancing
What It Is
Distributing requests across multiple instances of a service to maximize throughput, minimize latency, and avoid overloading any single instance.
Why You Need It

Horizontal scaling: Run 10 pods instead of 1 huge one
High availability: If one pod dies, others handle the load
Performance: Spread load evenly to avoid hot spots
Locality awareness: Prefer pods in the same AZ to reduce latency

Without Istio
Kubernetes gives you basic load balancing via Services:
yaml# Just gets round-robin at L4 (TCP)
apiVersion: v1
kind: Service
metadata:
  name: user-service
spec:
  selector:
    app: user-service
  ports:
  - port: 80
    targetPort: 8080
Limitations:

Only round-robin or random: No smart algorithms
No awareness of load: Sends traffic to overloaded pods
No circuit breaking: Sends traffic to failing pods
No locality preferences: Might route cross-AZ unnecessarily
L4 only: Load balancing happens at TCP level, not HTTP

With Istio
yamlapiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: user-service-lb
spec:
  host: user-service
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST  # Or ROUND_ROBIN, RANDOM, PASSTHROUGH
      localityLbSetting:
        enabled: true
        failover:
        - from: us-east-1a
          to: us-east-1b
    connectionPool:
      http:
        http2MaxRequests: 100
        maxRequestsPerConnection: 10
Advanced Load Balancing Options:

LEAST_REQUEST: Send to pod with fewest active requests (best for uneven workloads)
RANDOM: Good default, better than round-robin for distributed systems
CONSISTENT_HASH: Route same user/session to same pod (sticky sessions)
Locality-aware: Prefer pods in same AZ, fail over if none available
Weighted routing: 80% to v1, 20% to v2 (for canary deployments)

Benefits:

L7 (HTTP) load balancing with connection pooling
Circuit breaking integration: Don't route to ejected pods
Observability: See load distribution across pods
Dynamic: Automatically adjusts to pod scaling events
No code changes, works for all services

Backstage applies template-level governance (e.g., which service blueprints can be deployed and how).

Together, this creates an intent-based platform — you declare the intent (“what”) and the system handles the implementation (“how”).
