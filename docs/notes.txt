```text
OpenShift Cross-Region API Connectivity Checklist

Goal:
Enable private API connectivity between OpenShift clusters/VPCs across two AWS regions using Transit Gateway peering.

Example traffic paths:
- East jumpbox -> West OpenShift API on TCP 6443
- West jumpbox -> East OpenShift API on TCP 6443


1. Connectivity Components Required

The following infrastructure components must exist:

- East VPC
- West VPC
- East Transit Gateway
- West Transit Gateway
- East VPC attachment to East TGW
- West VPC attachment to West TGW
- TGW peering attachment between East TGW and West TGW
- Private DNS / Route 53 hosted zone association so the remote API hostname resolves privately

The TGW peering attachment is only the inter-region connection. It does not automatically make the VPCs route to each other. Route table entries are still required on both sides.


2. Route Table Requirements

Routing has two layers:

- VPC subnet route tables
- TGW route tables

The VPC subnet route table sends traffic to the local TGW.

The TGW route table decides which TGW attachment receives the traffic next.


2.1 East-to-West Path

For traffic from East to West:

East VPC subnet route table:
Destination: West VPC CIDR
Target:      East TGW / East TGW attachment option

East TGW route table:
Destination: West VPC CIDR
Target:      TGW peering attachment

West TGW route table:
Destination: East VPC CIDR
Target:      West VPC attachment

West VPC subnet route table:
Destination: East VPC CIDR
Target:      West TGW / West TGW attachment option

The West VPC subnet route is required for return traffic. Without it, the request may arrive, but the response cannot return to the East source.


2.2 West-to-East Path

For traffic from West to East:

West VPC subnet route table:
Destination: East VPC CIDR
Target:      West TGW / West TGW attachment option

West TGW route table:
Destination: East VPC CIDR
Target:      TGW peering attachment

East TGW route table:
Destination: West VPC CIDR
Target:      East VPC attachment

East VPC subnet route table:
Destination: West VPC CIDR
Target:      East TGW / East TGW attachment option

The East VPC subnet route is required for return traffic.


3. Security Group Requirements

For OpenShift API testing, the important port is:

TCP 6443

For East jumpbox -> West OpenShift API:

West API load balancer SG:
Inbound TCP 6443 from East VPC CIDR

West master/control-plane SG:
Inbound TCP 6443 from East VPC CIDR, if the masters see the original East source IP

For West jumpbox -> East OpenShift API:

East API load balancer SG:
Inbound TCP 6443 from West VPC CIDR

East master/control-plane SG:
Inbound TCP 6443 from West VPC CIDR, if the masters see the original West source IP

The master/control-plane SG may or may not be required depending on how the load balancer and target group preserve client source IP. During troubleshooting, the safer setup is to allow TCP 6443 from the remote VPC CIDR on both:

- API load balancer SG
- master/control-plane SG


4. NACL Requirements

NACLs are stateless. Both the forward request and return response must be allowed.

For East jumpbox -> West API on TCP 6443:

East jumpbox subnet outbound:
Allow TCP 6443 to West VPC CIDR

West API subnet inbound:
Allow TCP 6443 from East VPC CIDR

West API subnet outbound:
Allow TCP ephemeral ports to East VPC CIDR

East jumpbox subnet inbound:
Allow TCP ephemeral ports from West VPC CIDR

For West jumpbox -> East API on TCP 6443, mirror the same rules.

Typical ephemeral range:

TCP 1024-65535

Some environments use a narrower approved ephemeral range. The key point is that return traffic does not come back to the client on TCP 6443. It returns to the client source port, which is usually an ephemeral port.


5. DNS Requirements

The API hostname used by the remote jumpbox must resolve to the private API endpoint.

Typical OpenShift API hostname:

api.<cluster-name>.<base-domain>

Internal API hostname may also exist:

api-int.<cluster-name>.<base-domain>

Verify from the source jumpbox:

dig +short api.<cluster-name>.<base-domain>

Expected result:
A private IP associated with the target cluster API endpoint.

If DNS resolves to the wrong endpoint, an old record, a public IP, or nothing, the routing and security configuration can be correct but curl will still fail.


6. Basic Test Command

From the source jumpbox:

curl -vk --connect-timeout 5 https://api.<cluster-name>.<base-domain>:6443/version

Useful result meanings:

Connected:
Network path works. Remaining issues are TLS, API, or authentication related.

Connection timed out:
Usually routing, TGW route table association, security group, NACL, or return path issue.

Connection refused:
Routing reached something, but the destination IP/port is wrong or the service is not listening.

No route to host:
Usually local subnet routing or host/network-level routing problem.


7. Mental Model

The correct mental model is:

VPC subnet route table:
Sends remote VPC CIDR traffic to the local TGW.

Local TGW route table:
Sends remote VPC CIDR traffic to the TGW peering attachment.

Remote TGW route table:
Receives traffic from peering and sends it to the remote VPC attachment.

Remote VPC subnet route table:
Must know how to send replies back to the opposite VPC CIDR.

Security groups:
Must allow TCP 6443 on the API side.

NACLs:
Must allow TCP 6443 forward traffic and ephemeral return traffic.


8. Main Items Changed During Troubleshooting

The main fixes were:

- Added remote VPC CIDR routes to subnet route tables on both sides.
- Confirmed TGW route tables and TGW peering routes.
- Confirmed the TGW attachment associations were using the route tables containing the needed routes.
- Added or confirmed TCP 6443 on the API load balancer security group.
- Added or confirmed TCP 6443 on master/control-plane security groups where needed.
- Confirmed NACLs allowed forward TCP 6443 traffic and return ephemeral traffic.

Adding TCP 6443 to the API load balancer security group was definitely required in this case because connectivity began working after that change.
```
