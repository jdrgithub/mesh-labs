Private jumpbox
  ↓
Jumpbox security group egress
  ↓
Private subnet NACL outbound
  ↓
Private subnet route table
  ↓
NAT Gateway in a public subnet
  ↓
Public subnet route table
  ↓
Internet Gateway
  ↓
Internet
  ↓
Registry endpoint, for example registry.redhat.io / quay.io / docker.io
==========================================================================

What must be true
1. Jumpbox security group

The jumpbox SG must allow outbound HTTPS:

Outbound:
TCP 443 to 0.0.0.0/0

or at least to the registry IP ranges, though 0.0.0.0/0 is the normal test rule.

Security groups are stateful, so inbound return traffic does not need a separate SG rule.

2. Private subnet route table

The route table associated with the private jumpbox subnet needs:

Destination: 0.0.0.0/0
Target:      NAT Gateway

Not the internet gateway.

So for a private subnet:

0.0.0.0/0 → nat-xxxxxxxx
3. NAT Gateway subnet

The NAT Gateway must live in a public subnet.

That public subnet’s route table needs:

Destination: 0.0.0.0/0
Target:      Internet Gateway

So for the NAT subnet:

0.0.0.0/0 → igw-xxxxxxxx

If the NAT Gateway is in a subnet that does not route to an IGW, private instances can route to the NAT but the NAT cannot reach the internet.

4. NAT Gateway public IP

The NAT Gateway must have an Elastic IP / public address.

For AWS NAT Gateway, this is normally part of creating a public NAT Gateway.

5. Private subnet NACL

The NACL on the private jumpbox subnet must allow the outbound HTTPS request and the inbound ephemeral return traffic.

Minimum logic:

Outbound:
Allow TCP 443 to 0.0.0.0/0

Inbound:
Allow TCP 1024-65535 from 0.0.0.0/0

The return packet comes back to the jumpbox’s random source port, not port 443.

6. Public NAT subnet NACL

The NACL on the NAT Gateway’s public subnet must allow NAT traffic in both directions.

Minimum logic:

Inbound:
Allow TCP 443 from private subnet CIDR

Outbound:
Allow TCP 443 to 0.0.0.0/0

Inbound:
Allow TCP 1024-65535 from 0.0.0.0/0

Outbound:
Allow TCP 1024-65535 to private subnet CIDR

Many environments simplify this by allowing all outbound and appropriate inbound ephemeral/HTTPS ranges on the NAT subnet NACL.

Practical troubleshooting order

Check these in this order:

1. Private jumpbox subnet route table:
   0.0.0.0/0 → NAT Gateway

2. NAT Gateway subnet route table:
   0.0.0.0/0 → Internet Gateway

3. NAT Gateway state:
   Available

4. Jumpbox SG outbound:
   TCP 443 to 0.0.0.0/0

5. Private subnet NACL:
   outbound 443 allowed
   inbound ephemeral return allowed

6. NAT public subnet NACL:
   private subnet → internet 443 allowed
   internet → private subnet ephemeral return allowed

7. DNS:
   registry hostname resolves

8. Test:
   curl -vk https://registry.redhat.io

The most common break is:

Private subnet has no default route to NAT

or:

NAT Gateway subnet does not have default route to IGW

or:

NACL allows 443 but blocks ephemeral return traffic

  tasks:

      retries: 30
      delay: 10

      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: v1
          kind: Secret
          metadata:
            name: datagrid-auth
            namespace: "{{ datagrid_namespace }}"
          type: Opaque
          stringData:
            identities.yaml: |
              credentials:

                  password: {{ datagrid_password }}
                  roles:
                    - admin

      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: infinispan.org/v1
          kind: Infinispan
          metadata:
            name: "{{ datagrid_cluster_name }}"

            labels:
              site: "{{ datagrid_site_name }}"
          spec:
            replicas: "{{ datagrid_replicas }}"

              type: DataGrid
              container:
                storage: "{{ datagrid_storage }}"
            security:
              endpointAuthentication: true

    - name: Wait for Data Grid cluster to become WellFormed

        kind: Infinispan
        name: "{{ datagrid_cluster_name }}"
        namespace: "{{ datagrid_namespace }}"
      register: datagrid_cr
      until: >
        datagrid_cr.resources | length > 0 and
        (
          datagrid_cr.resources[0].status.conditions | default([])
          | selectattr('type', 'equalto', 'WellFormed')
          | selectattr('status', 'equalto', 'True')
          | list
          | length
        ) > 0
      retries: 60
      delay: 10

    - name: Show Data Grid services
      kubernetes.core.k8s_info:
        api_version: v1
        kind: Service
        namespace: "{{ datagrid_namespace }}"
      register: datagrid_services

    - name: Print Data Grid services
      ansible.builtin.debug:
        msg: "{{ datagrid_services.resources | map(attribute='metadata.name') | list }}"

A few corrections/notes are important before this goes into automation.

For **cross-site**, Data Grid Operator uses the `spec.service.sites.local.name`, `spec.service.sites.local.expose.type`, and `spec.service.sites.locations` fields. The operator supports `NodePort`, `LoadBalancer`, and `Route`; if using `Route`, Red Hat says a keystore is required, and cross-site replication does not support the OpenShift service CA, so custom certificates are needed for that cross-site encryption path. ([Red Hat Documentation][2])

For **Keycloak-required caches**, the Red Hat build of Keycloak HA guide calls out these Data Grid caches as required: `actionTokens`, `authenticationSessions`, `loginFailures`, and `work`. It also recommends creating them with Data Grid `Cache` CRs before Keycloak starts. ([Red Hat Documentation][3])

For **Keycloak remote cache**, the remote Data Grid Hot Rod port is normally:

```text
11222
```

That is different from the cross-site Data Grid replication port, which is commonly:

```text
7900
```

So keep these separate:

```text
Keycloak -> local Data Grid:
  TCP 11222

East Data Grid <-> West Data Grid cross-site:
  TCP 7900, or whatever xsite expose port is configured
```

For a private AWS/OpenShift setup, the most practical first pass is usually:

```text
Data Grid xsite expose type:
  LoadBalancer

LB type:
  internal

Network:
  allow East Data Grid xsite endpoint <-> West Data Grid xsite endpoint

Keycloak:
  only talks to local Data Grid service on 11222
```

The playbook above assumes the remote OpenShift service account token secret already exists. That part is normally a separate setup step because each cluster needs a token that allows the local Data Grid Operator to inspect/connect to the remote site. Red Hat explicitly lists service account token exchange as a prerequisite for managed cross-site connections. ([Red Hat Documentation][2])

YUGABYTE STUFF
=======================================
Below is the guidance to give the Yugabyte side. This is written as requirements, not as a question list.

```text
YugabyteDB xCluster Requirements for Keycloak Active/Standby DR

Goal:
Support manual DNS failover for Keycloak across East and West OpenShift clusters.

Important distinction:
Infinispan / Red Hat Data Grid handles the Keycloak cache/session cross-site layer.
YugabyteDB xCluster handles the persistent relational database replication layer.

These are separate layers and both are required.
Infinispan does not replicate the Yugabyte database.
Yugabyte xCluster does not replace Infinispan/Data Grid.


1. Required Yugabyte Topology

Set up two independent YugabyteDB universes:

East Yugabyte universe:
  Normal active/source database side.
  Keycloak writes here during normal operation.

West Yugabyte universe:
  Standby/target database side.
  Receives replicated Keycloak database changes from East.
  Becomes the writable database side during manual failover.

Replication model:
  Use YugabyteDB xCluster replication.
  Start with unidirectional active/standby replication:

    East -> West

Do not configure bidirectional/multi-writer replication unless the architecture explicitly calls for that. For this Keycloak manual failover pattern, the safer model is single-writer active/standby.

Yugabyte describes xCluster as asynchronous replication between independent YugabyteDB universes, with a source/producer universe and a target/consumer universe. It supports unidirectional and bidirectional replication, but this design should use unidirectional active/standby. 
Source: YugabyteDB xCluster documentation.

7. Manual Failover Requirement

Manual DNS switchover is only the traffic-routing step. The database failover procedure must happen before or alongside DNS movement.

Required manual failover flow:

  1. Declare East failed or intentionally stop East Keycloak.
  2. Ensure only one Keycloak side can write.
  3. Prevent split brain.
  4. Pause/stop/transition xCluster according to Yugabyte procedure.
  5. Promote or enable West Yugabyte for writes.
  6. Start or enable West Keycloak against West Yugabyte.
  7. Manually switch DNS to West Keycloak.
  8. After East recovers, decide whether to rebuild East, reverse replication, or fail back using the documented Yugabyte procedure.

The key rule:
  Do not allow East Keycloak and West Keycloak to write to independent databases at the same time.

9. Relationship to Infinispan/Data Grid

Infinispan/Data Grid:
  Keycloak cache/session cross-site layer.
  Installed and configured separately from Yugabyte.
  Handles Keycloak distributed cache and cross-site cache behavior.

Yugabyte xCluster:
  Persistent relational database replication layer.
  Configured between Yugabyte universes.
  Handles durable Keycloak database state.

Both are used together:

  Keycloak active/standby HA = DNS failover + Data Grid/Infinispan cache HA + Yugabyte xCluster database replication.
```

The two most important asks are: **configure East → West xCluster for the Keycloak database**, and **provide a written DB failover/promote/failback runbook**. Yugabyte xCluster is asynchronous, so the team also needs to state the expected RPO and how replication lag will be checked before a planned DNS switchover.
