You’re right. A clearer way to describe this is to separate **what exists** from **what rules must be added to it**.

There are really four categories:

```text
1. Connectivity components
2. Route table entries
3. Security group rules
4. NACL rules
```

## 1. Connectivity components that must exist

For East ↔ West private API access, these are the infrastructure pieces:

```text
East VPC
West VPC

East TGW
West TGW

East VPC attachment to East TGW
West VPC attachment to West TGW

TGW peering attachment between East TGW and West TGW

Private hosted zone / DNS association
so api.<cluster-domain> resolves to the private API endpoint
from the opposite VPC
```

Those are the “wires.”

Nothing works until those exist.

## 2. Route table entries that must exist

Routing is where each side says, “to reach the other VPC CIDR, send traffic this way.”

### East-to-West direction

For traffic from East to West:

```text
East VPC subnet route table
Destination: West VPC CIDR
Target:      East TGW / East TGW attachment option
```

```text
East TGW route table
Destination: West VPC CIDR
Target:      TGW peering attachment
```

```text
West TGW route table
Destination: East VPC CIDR
Target:      West VPC attachment
```

```text
West VPC subnet route table
Destination: East VPC CIDR
Target:      West TGW / West TGW attachment option
```

That last one is the return path. Without it, the request may arrive, but the response cannot get back.

### West-to-East direction

For traffic from West to East:

```text
West VPC subnet route table
Destination: East VPC CIDR
Target:      West TGW / West TGW attachment option
```

```text
West TGW route table
Destination: East VPC CIDR
Target:      TGW peering attachment
```

```text
East TGW route table
Destination: West VPC CIDR
Target:      East VPC attachment
```

```text
East VPC subnet route table
Destination: West VPC CIDR
Target:      East TGW / East TGW attachment option
```

So yes, the subnet route tables on **both sides** need remote CIDR routes. The TGW route tables also need their own remote CIDR routes.

## 3. Security group rules that must exist

For OpenShift API testing, the important port is:

```text
TCP 6443
```

If testing:

```text
East jumpbox → West OpenShift API
```

then West needs to allow:

```text
West API load balancer SG
Inbound TCP 6443 from East VPC CIDR
```

And possibly:

```text
West master/control-plane SG
Inbound TCP 6443 from East VPC CIDR
```

For the reverse:

```text
West jumpbox → East OpenShift API
```

East needs to allow:

```text
East API load balancer SG
Inbound TCP 6443 from West VPC CIDR
```

And possibly:

```text
East master/control-plane SG
Inbound TCP 6443 from West VPC CIDR
```

The reason the master SG is a “possibly” is that it depends on where AWS preserves the original client source IP. If the masters see the remote jumpbox IP, the master SG needs the remote VPC CIDR. If they only see load-balancer-side traffic, the LB SG may be enough.

In practice, allowing `6443` from the remote VPC CIDR on both the API LB SG and master/control-plane SG is the safer troubleshooting setup.

## 4. NACL rules that must exist

NACLs are stateless, so both the request and response must be allowed.

For:

```text
East jumpbox → West API :6443
```

the minimum NACL logic is:

```text
East jumpbox subnet outbound
Allow TCP 6443 to West VPC CIDR
```

```text
West API subnet inbound
Allow TCP 6443 from East VPC CIDR
```

```text
West API subnet outbound
Allow TCP ephemeral ports to East VPC CIDR
```

```text
East jumpbox subnet inbound
Allow TCP ephemeral ports from West VPC CIDR
```

For the reverse direction, mirror that.

The ephemeral port range is usually:

```text
1024-65535
```

or whatever narrower range your environment standard uses. The key idea is that the return packet does **not** come back to the client on `6443`; it comes back to the client’s random source port.

## Cleaner mental model

The setup is not just:

```text
TGW peering exists, therefore it works
```

It is:

```text
VPC subnet route table gets traffic to the local TGW.

Local TGW route table sends remote CIDR traffic to the peering attachment.

Remote TGW route table receives traffic from peering and sends it to the remote VPC attachment.

Remote VPC subnet route table must know how to send replies back to the opposite VPC.

Security groups must allow 6443 at the API side.

NACLs must allow both 6443 forward traffic and ephemeral return traffic.
```

The main things you changed were probably:

```text
1. Added remote CIDR routes to subnet route tables on both sides.
2. Confirmed TGW route tables and peering routes.
3. Added/confirmed 6443 on the API load balancer SG.
4. Possibly added/confirmed 6443 on master/control-plane SGs.
```

The part that definitely mattered based on your result: adding `6443` to the API load balancer SG fixed at least one direction.
