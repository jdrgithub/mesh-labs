

1. Create a realm in Keycloak
Create a dedicated realm for OpenShift authentication.
Example:
openshift
The realm URL becomes:
https://<keycloak-host>/realms/openshift
This URL is the OIDC issuer OpenShift will use.

2. Create the OpenShift client in Keycloak
In the realm:
Clients → Create
Set:
Client ID: openshift-console-client
Client type: OpenID Connect
After creation configure:
Client authentication: ON
Standard Flow: ON
Direct Access Grants: OFF

3. Configure redirect URIs
In the client settings add:
https://oauth-openshift.apps.<cluster-domain>/oauth2callback/*
This allows the OAuth callback from OpenShift.

4. Capture the Keycloak client secret
In the client:
Clients → openshift-console-client → Credentials
Copy the client secret.

5. Store the client secret in OpenShift
Create the secret referenced by the OAuth config.
oc create secret generic keycloak-client-secret \
 -n openshift-config \
 --from-literal=clientSecret=<KEYCLOAK_SECRET>

6. Configure the OpenShift OAuth identity provider
Edit the OAuth object:
oc edit oauth cluster
Add an OpenID provider.
Example:
identityProviders:
- name: keycloak
 mappingMethod: claim
 type: OpenID
 openID:
   clientID: openshift-console-client
   clientSecret:
     name: keycloak-client-secret
   issuer: https://<keycloak-host>/realms/openshift
   claims:
     preferredUsername:
     - preferred_username
     name:
     - name
     email:
     - email
     groups:
     - groups
OpenShift automatically reloads the OAuth server.

7. Configure group mapping in Keycloak
In Keycloak create an admin group:
system:masters
Add your user to that group.

8. Add a groups mapper
In the client scope (often the automatically created scope):
openshift-console-client-dedicated
Create a mapper:
Mapper type: Group Membership
Name: groups
Token Claim Name: groups
Add to ID token: ON
Add to access token: ON
Add to userinfo: ON
This ensures the token contains:
groups: ["system:masters"]

9. Verify user claims
The token returned by Keycloak must include:
preferred_username
groups
OpenShift uses these to create the user identity and map RBAC.

10. Login flow
The final authentication flow is:
OpenShift console
     ↓
oauth-openshift
     ↓
Keycloak login
     ↓
OIDC token returned
     ↓
OpenShift creates user
     ↓
RBAC via system:masters

11. Optional cleanup

1. Redirect Handler Error Means the IdP Was Never Activated
Initial error:
unable to locate redirect handler
Key insight:
This does not mean networking or Keycloak login failed.
It means:
OAuth server did not register the IdP internally
OpenShift only creates a redirect handler after the IdP successfully initializes.

2. The Authentication Operator Logs Are the Source of Truth
The critical evidence came from the authentication operator logs:
failed to apply IDP config
tls: failed to verify certificate
x509: certificate signed by unknown authority
This proved:
OAuth initialization failed
Therefore the IdP never became active.

3. Curl Tests With -k Masked the Real Problem
Earlier tests succeeded because they used:
curl -k
That bypasses TLS verification.
The OAuth server does not bypass TLS validation, so it rejected the Keycloak endpoint.
Key lesson:
Always test TLS the same way the service will.

4. The Fix Was Adding the Keycloak CA to OAuth
The successful fix was:
Provide the Keycloak CA bundle in the OAuth IdP configuration
Mechanism:
ConfigMap (openshift-config)
↓
Referenced in OAuth CR
↓
Authentication operator reloads config
↓
OAuth pods restart
↓
IdP successfully initializes
Once trusted, the OAuth server successfully loaded the provider.

5. Group Claim Mapping Can Break Authentication
After TLS was fixed, the next error appeared:
Group "system:masters" is invalid
Cause:
Keycloak groups claim included system:masters
OpenShift group objects cannot contain :.
Fix:
Remove or remap invalid groups from the Keycloak group mapper

6. Manual OAuth URLs Can Cause Parameter Errors
The later error:
error handling auth request: requested parameter not sent
was caused by testing with an incomplete authorization URL.
The correct approach:
Use the OpenShift console login flow
The console automatically generates the correct OAuth request.

After fixes:

8. Core Lessons for Future OIDC Troubleshooting
The most important diagnostic rules that emerged:
Rule 1
"unable to locate redirect handler"
= IdP failed initialization
Check authentication operator logs immediately.

Rule 2
Curl success does not prove TLS trust.
Verify certificate trust.

Rule 3
The authentication operator logs reveal IdP failures.
OAuth pod logs often do not.

Rule 4
OIDC group claims must be valid OpenShift group names.
Invalid characters will break login.

Final Summary
The successful resolution required fixing three separate layers:
TLS trust between OpenShift OAuth and Keycloak


Invalid group mapping from Keycloak claims


Correct OAuth authorization request parameters


Once those were resolved, the OIDC authentication flow worked as designed.

Export the certificate chain:

keycloak-ca.crt

oc create configmap keycloak-ca \

Here’s a clear, non-deep-technical summary suitable for a sprint update.

I worked on integrating Keycloak as the identity provider for the OpenShift cluster, enabling users to authenticate to OpenShift using centralized identity management rather than local accounts.
The work involved configuring OpenShift’s OAuth system to use Keycloak via OpenID Connect, setting up the required client configuration in Keycloak, and connecting the two systems so authentication tokens issued by Keycloak could be trusted by OpenShift.
During the implementation I ran into several issues that prevented the identity provider from activating. I systematically traced those down through the OpenShift authentication operator and OAuth components. The key problems turned out to be TLS trust between OpenShift and the Keycloak service, incorrect group mappings coming from Keycloak, and some parameter issues in the authentication request flow.
After resolving those, the OpenShift OAuth server was able to successfully initialize the Keycloak provider, redirect users to Keycloak for login, and accept the returned identity tokens.
The final result is that users can now authenticate to the OpenShift console through Keycloak, which enables centralized authentication and group-based access control going forward.
